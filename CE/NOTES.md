# PopGBA 技術メモ(SHARP Brain / Windows CE)

コードは AI(Claude)が書きました。製作者はプログラムを読めません。製作者がしたのは、AI への指示と、実機(PW-G5300)での確認です。

PopGBA を作る中でわかったことのうち、実機で確かめたことと、このリポジトリのコードで裏付けが取れることだけをまとめています。Brain 向けにほかのエミュレータを移植するとき、作業を始める前に AI に読ませることを想定しています。

実機で確かめた機種は SHARP Brain PW-G5300 だけです。ほかの機種での動作は確かめていません。

各項目の最後の( )は、もとにした開発メモの記録です。開発メモでは、作業の区切りを「ラウンド」と呼んでいます。開発メモはリポジトリに入れていません。( )が無い項目は、このリポジトリのコードで確かめたことです。ファイル名と関数名を書いています。

v1.0.0 より前の直しは、コミット 572c439(コアの直し)と dd2b895(フロントエンド)にまとめて入っています。

## 全体の作り

- PopGBA は libretro のフロントエンドとして作っています。`libretro/libretro.c` をそのままコンパイルし、`CE/ce_main.c` が `retro_init()`・`retro_load_game()`・`retro_run()` を呼び、画面・音・入力・環境のコールバック(`retro_set_*` に渡すもの)を実装しています。`retro_run()` は1フレーム分を動かして戻ります(`CE/Makefile` の冒頭のコメント)(開発メモのラウンド56、2026-09-02)
- コアのファイルは、上流と同じくリポジトリの一番上の階層にあり、`CE/Makefile` が `COREROOT := ..` で使います。今のコアは上流の libretro/gpsp の master(5819380、2026-09-19)です(開発メモの「v1.0.3 の1回目」、2026-10-04、コミット 46d283c、タグ v1.0.3)
- 開発の途中までは、上流の古い世代のコアに PopGBA が手を入れたものを使っていました。このメモでは「前のコア」と書きます。ラウンド56で、コアを上流の master に入れ替えました(開発メモのラウンド56、2026-09-02)
- コアで変えたファイルは `arm/arm_stub.S` と `cpu_threaded.c` の2つだけです。[`LICENSING.md`](LICENSING.md) の2節にまとめています(下の「コアで直したこと」)(開発メモのラウンド56、ラウンド57、どちらも 2026-09-02)
- `AppMain.exe` が使う DLL は `COREDLL.dll` だけです。`arm-mingw32ce-objdump -p AppMain.exe` で確かめられます(開発メモの「v1.0.7 の2回目」、2026-10-09)

## ビルド

- `CE/Makefile` は `-march=armv5te -mtune=arm926ej-s -mno-unaligned-access` を付けています。`-mno-unaligned-access` はコンパイラの設定なので、C から作るコードに効きます。手書きのアセンブリは、書いたとおりの命令になります(下の「JIT」の、4の倍数でない番地の項目)(開発メモのラウンド15、2026-08-14)
- `-mtune=arm926ej-s` は、付けても前のコアの実機のログで速さは変わりませんでした。実機の CPU に合わせた設定として残しています(開発メモのラウンド35、2026-08-31)
- `-flto` は使っていません(開発メモのラウンド35、2026-08-31)
- `cpu.cc`・`video.cc` は C++ なので `arm-mingw32ce-g++` でコンパイルしますが、リンクは `gcc` でしています。`cpu.o` に C++ のランタイムのシンボル(`__cxa_*`・`operator new`・`std::` など)が無いことを `nm` で確かめ、`libstdc++` はリンクしていません(開発メモのラウンド56、2026-09-02)
- コアが使う libretro-common の関数は、`filestream_*` の6つと `strlcpy`・`strlcat` だけでした(grep)。`filestream_*` は `CE/ce_filestream.c`(`fopen` を使う)で用意し、libretro-common からは `compat_strl.c` だけをコンパイルしています(開発メモのラウンド56、2026-09-02)
- `AppMain.exe` は PE/COFF の形式です。GNU as の説明書では、`.type`・`.size` は COFF と ELF で書き方が違い、COFF では `.def`/`.endef` の中で使います。`%function`・`%nobits` は ELF の書き方です。上流の `arm/arm_stub.S` の ELF 向けの `.type`・`.size` は外しています(下の「コアで直したこと」)(開発メモのラウンド56、2026-09-02、as.info で確認、2026-10-09)
- cegcc のヘッダ(`winbase.h`)では、`_WIN32_WCE` のとき `GetProcAddress` は `GetProcAddressW` の別名です。`GetCurrentProcess()` は `kfuncs.h` で、決まった値(2 + 64 = 0x42)を返す inline の関数として書かれています(開発メモのラウンド32、2026-08-31、cegcc のヘッダで確認、2026-10-09)
- gcc では `__try`/`__except` は使えません(PC の gcc でも同じエラーになります)。PopGBA は使っていません。cegcc の `windef.h` では、`__SEH_NOOP` を定義したときだけ、`__try` は空に、`__except` の中は実行されない形に置き換わります(開発メモのラウンド44、2026-09-02、PC の gcc と cegcc のヘッダで確認、2026-10-09)
- この環境の gcc では、変数に付ける `aligned` の上限は 8 バイトです(gcc の `config/arm/wince-pe.h` の `BIGGEST_ALIGNMENT` が 64 ビット)。翻訳したコードを置く場所は、`arm/arm_stub.S` の中で `.align 4` を付けて置いています(開発メモのラウンド44、2026-09-02、gcc の wince-pe.h で確認、2026-10-09)
- GNU as の ARM の書き方は、既定では divided です。divided では、条件付きのハーフワードの読み書きは `ldrneh`・`strneh` と書きます。`.syntax unified` のときは `ldrhne`・`strhne` です(開発メモのラウンド37、2026-08-31、as.info で確認、2026-10-09)
- ARM の命令の決まりで、`ldrh`・`strh` の番地は、レジスタにシフトを付けない形です。ARM の命令の即値は「8ビットの値を偶数ビット回したもの」で、`#0x3FF` はこの形になりません(binutils の `tc-arm.c` の `encode_arm_addr_mode_3()`・`encode_arm_immediate()`)。この形にならないものは、ほかの命令の組み合わせで書いています(開発メモのラウンド37、2026-08-31、binutils の tc-arm.c で確認、2026-10-09)
- `ldr rX, =symbol` の値はリテラルプールに置かれ、命令からの距離は 4095 バイトまでです(binutils の `tc-arm.c` の `validate_offset_imm()`)。`arm/arm_stub.S` にコードを足したときは、足した部分の前に `.ltorg` を入れています(開発メモのラウンド49、2026-09-02、binutils の tc-arm.c で確認、2026-10-09)

## 画面

- 画面の大きさは `GetSystemMetrics(SM_CXSCREEN / SM_CYSCREEN)` で取っています(`ce_gapi.c`)。実機では 480×320 でした(実機のログ)(開発メモのラウンド2、2026-08-10)
- GBA の 240×160 は、ちょうど2倍で 480×320 になります。表示の大きさは x1(等倍、中央)と x2 の2つだけにしました。x1・x2 とも実機で表示を確かめました(開発メモのラウンド13、2026-08-13〜2026-08-14)
- GAPI(`gx.dll`)は使っていません。画面と同じ大きさの RGB565 の DIB セクション(`BI_BITFIELDS`、`biHeight` を負にして上から下の順)にアプリのコードで拡大して書き、`BitBlt` で等倍のまま画面へ送ります(`ce_gapi.c`。ファイル名は GAPI のころのまま)(開発メモのラウンド35、2026-08-31)
- x2 は、元の1画素を `p | (p << 16)` で32ビット1回に2画素ぶん書き、2行目は1行目を `memcpy` しています(`ce_gapi.c` の `GapiBlitRGB565()`)。前のコアの実機のログ(`perf: blit`)で、転送は x2 で平均 7〜8ms、x1 で約2ms でした(開発メモのラウンド36、2026-08-31)
- GDI でウィンドウに直接描くので、ダイアログを閉じて見えた部分は描き直します。`ce_main.c` の `WndProc` の `WM_PAINT` で `ce_gapi.c` の `GapiForceRepaint()` を呼び、DIB セクションに残っている最後の画面を送り直します
- メニューや設定画面の文字は、`AppMain.exe` に入れたビットマップフォントで描いています(`ce_bmpfont.c`)。TrueType のフォントファイルを端末から消しても、日本語の画面がすべて表示されることを実機で確かめました(開発メモのラウンド31、2026-08-30)。今の既定のフォントは Galmuri14 です(`CE/Makefile`)(開発メモの「メニューのフォントを Galmuri14 に」、2026-09-27)
- メインメニューのマスコットの絵は、背景のクリーム色と合成した 24 ビットの BMP にしています(開発メモのラウンド64、2026-09-25)

## 速さ

- 前のコアでは、`retro_run` の平均はインタプリタで 43〜47ms、JIT で 23〜30ms でした(実機のログ。比べたゲームは同じとは限りません)(開発メモのラウンド4、ラウンド12、どちらも 2026-08-12)
- 今のコアにしたあとの実機のログ(JIT)では、フレームスキップ 0 での `retro_run` の平均は『スーパーストリートファイターII X リバイバル』が 30〜32ms、『クロノアヒーローズ 伝説のスターメダル』が 21〜26ms でした。前のコア(計測用のコードが入ったビルド)では、それぞれ 37〜40ms、28〜31ms でした(開発メモのラウンド60、2026-09-02)
- 同じログで、フレームスキップ 3〜4 では `retro_run` の平均は 13〜18ms でした。フレームスキップ 3 の『クロノアヒーローズ』では、約82秒のあいだ `audio underrun` のログが1行も出ませんでした。フレームスキップ 0 では underrun が出続けました(開発メモのラウンド60、2026-09-02)
- 目標の 16.7ms(59.73fps)には、フレームスキップ 0 では届きません。設定の既定はフレームスキップ 4 です(`ce_video.c` の `s_frameSkip`)(開発メモのラウンド34、2026-08-31、ラウンド60、2026-09-02)
- フレームスキップ(Video Config の 0〜30)は、コアの `gpsp_frameskip` の `auto` を使います。コアは、音のバッファが足りなくなりそうなときにフレームを飛ばします。続けて飛ばす数の上限はコアでは 30 で決まっているので、設定した数に達したら、音のバッファの状態を「足りなくならない」と答えて、そのフレームを描かせます(`ce_video.c` の `CeVideoFrameSkipShouldForceRender()`)。設定の数が、コアの `gpsp_frameskip_interval` に渡ることはありません(開発メモのラウンド57、2026-09-02)
- フレームスキップが ON のときだけ、音のリングが 45% より少なくなると `Sleep()` をやめて `retro_run()` を続けて回し、75% まで戻ったら元の速さに戻します。このあいだは、コアにフレームを飛ばさせます(`ce_main.c` の `CE_AUDIO_CATCHUP_LOW_PCT`・`CE_AUDIO_CATCHUP_OK_PCT`)。フレームスキップ 0 のときは働きません(開発メモのラウンド34、2026-08-31)
- 前のコアの実機のログで、フレームスキップを 0 から 3 にすると、`retro_run` の平均は 25〜27ms から 15〜17ms に、underrun は1秒に約33.6回から約10.5回になりました(開発メモのラウンド34、2026-08-31)
- 前のコアで速くしようとした次の2つは、実機のログで速さが変わりませんでした(開発メモのラウンド35、ラウンド37、どちらも 2026-08-31)
  - JIT から C の関数を呼ぶ命令を、3語から1語にする
  - BG の合成のループをアセンブリにする。『スーパーストリートファイターII X リバイバル』の対戦中、PPU の描画は `cpu_thread` の約33〜38%でした

### JIT

- JIT の ON・OFF は、`PopGBA.cfg` の `VideoDynarec`(1 = ON、0 = インタプリタ)で切り替えます。設定の画面には入れていません。既定は ON で、cfg が無い状態で JIT が既定で動くことを実機で確かめました(開発メモのラウンド60、2026-09-02、同じ節の 2026-10-03 の追記)
- コアは、`gpsp_drc` の問い合わせに答えないと JIT を ON にします。OFF にできるように、`ce_video.c` の `CeVideoEnvGetVariable()` はいつも答えています(開発メモのラウンド57、2026-09-02)
- 翻訳したコードを置く場所(`rom_translation_cache`・`ram_translation_cache`)は、`arm/arm_stub.S` で `.bss` に置いています。上流は ELF の書き方(`.section .jit,"awx",%nobits`)で実行できるセクションに置いています。PopGBA は PE/COFF なので `.bss` を使っています。PW-G5300 では、`.bss` に置いたコードを JIT で実行できました(開発メモのラウンド60、2026-09-02、as.info で確認、2026-10-09)
- `.bss` に置くと、exe と翻訳したコードの距離は、ARM の `BL`・`B` が届く ±32MiB の中に収まります(`arm/arm_stub.S` のコメント)。前のコアで `VirtualAlloc(NULL, …)` で 10MiB を取ったときは `0x026F0000` に置かれ、exe の終わり(`0x00399000`)から約35MiB 離れていました(実機のログ)(開発メモのラウンド7、2026-08-12)
- `VirtualAlloc` で番地を指定して exe の近く(`0x00400000`〜`0x01400000` の5か所)に取ろうとしたら、5か所とも error=87 で取れませんでした。番地を指定しないと `0x02650000` に置かれ、exe の終わりから約34MiB 離れました(実機のログ)(開発メモのラウンド2a、2026-08-31)
- `GetModuleHandleW(NULL)` は、PW-G5300 では `0x00000042` を返しました。これを exe の先頭の番地として読んだら、Access Violation の例外で落ちました(BER の記録)(開発メモのラウンド2a、2026-08-31)
- 上流の ARM 向けのコードは、翻訳したあと `__clear_cache()` を呼びます。gcc の `__clear_cache()` は OS ごとの定義(`CLEAR_INSN_CACHE`)を使う関数で、gcc のソースの `config/arm` では Linux・BSD 向けに定義があります。Windows CE では、PopGBA は `cpu_threaded.c` の `platform_cache_sync()` で `CacheSync(CACHE_SYNC_ALL)` を呼んで同期しています。`CacheSync` の宣言は `cpu_threaded.c` に書いています(開発メモのラウンド5、2026-08-12、ラウンド56、2026-09-02、gcc のソースで確認、2026-10-09)
- `CacheRangeFlush` は PW-G5300 の `coredll.dll` にあり、範囲を指定してキャッシュを同期できました。前のコアで、翻訳のたびの `CacheSync(CACHE_SYNC_ALL)` を `CacheRangeFlush` にしたら、ROM を読み込んだ直後の最初の60フレームの `cpu_thread` の最大が 11,943ms から 230ms になりました。それより後の速さは変わりませんでした(開発メモのラウンド12、2026-08-12、ラウンド32、2026-08-31)
- そのあと、JIT で落ちるゲームを調べるときに `CacheSync(CACHE_SYNC_ALL)` に戻しましたが、落ちるのは変わりませんでした。今も `CacheSync(CACHE_SYNC_ALL)` を使っています(開発メモのラウンド44、ラウンド45、どちらも 2026-09-02)
- 前のコアでは、『Sweet Cookie Pie』『テイルズ オブ ファンタジア』『真・女神転生デビルチルドレン 炎の書』の3本が、JIT で毎回同じ場面で落ちるか止まりました。インタプリタでは動きました(開発メモのラウンド44〜ラウンド48、2026-09-02)
  - 次の3つを試しましたが、3本とも変わりませんでした: `CacheSync(CACHE_SYNC_ALL)` に戻す(ラウンド45)、翻訳する2つの関数を `-O1` でコンパイルする(ラウンド47)、BIOS の SWI 16個を C で書いた処理に置き換える(ラウンド49、ラウンド50)(どれも 2026-09-02)
  - コアを上流の master に入れ替えたら、3本とも JIT で動きました(開発メモのラウンド60、2026-09-02)。上流の 2026-09-19 までの直しを取り込んだあとも、この3本と『クロノアヒーローズ 伝説のスターメダル』『スーパーストリートファイターII X リバイバル』が JIT で動くことを確かめました(開発メモの「v1.0.3 の4回目」、2026-10-05、タグ v1.0.3)
- 前のコアの手書きのアセンブリ(`execute_store_u32` の `str`)で、4の倍数でない番地に書くと、Datatype Misalignment の例外で落ちました(BER の記録、『クレヨンしんちゃん』)。書く前に番地の下のビットを0にしたら、起動するようになりました(開発メモのラウンド15、2026-08-14)。その直しを外したビルドでは、32ビットの読み込み(`execute_load_u32` の `ldr`)でも同じ例外で落ちました(『テイルズ オブ ファンタジア』)(開発メモのラウンド45、2026-09-02)。今のコアの `arm/arm_stub.S` は、書く前に番地の下のビットを0にしています(`store_align_16()`・`store_align_32()`)(開発メモのラウンド56、2026-09-02)
- JIT が ON のときに別の ROM を開くと、新しい ROM のパスを付けて `AppMain.exe` をもう一度起動し、今のプロセスは終わります(`ce_main.c` の `RestartProcess()`)。前のコアでは、同じプロセスの中で2本目の ROM を読み込むと止まり、インタプリタでは止まりませんでした。プロセスを起動し直す形にして、切り替えられるようになりました(実機)(開発メモのラウンド14、2026-08-13〜2026-08-14、ラウンド15、2026-08-14)
- 新しいプロセスは `CREATE_SUSPENDED` で作り、`ResumeThread()` は古いプロセスが `retro_deinit()` まで終えてから呼びます(`CeShutdown()`)。前のコアで、すぐに `ResumeThread()` していたときは、新しいプロセスで翻訳用の約11MiB の `VirtualAlloc` が error=8 になることがありました。順番を変えたあと、5本・4回の切り替えで error=8 は出ませんでした(実機のログ)(開発メモのラウンド26、2026-08-14)

## 音

- `ce_audio.c` の `OpenAudioDevice()` は、waveOut を1チャンネル(`nChannels = 1`)で開きます。コアの左右の音は、`CeAudioPushSamples()` で平均して1つにしています
- コアの音の周波数は 65536Hz です。PopGBA はコアの `gpsp_sound_rate` の問い合わせに答えないので、コアは 65536Hz にします(`libretro.c`)(開発メモのラウンド57、2026-09-02)
- ROM を読み込むと画面が白いまま動かず、ログに `ring overrun` が出続けました。出力の周波数やビット数を変えても同じでした。周波数を変える計算で、65536 を32ビットのまま16ビット左にずらしていて、結果が 0 になり、音を作るループが終わっていませんでした。64ビットで計算するように直したら、白い画面は出なくなりました(実機)(`ce_audio.c` の `OpenAudioDevice()`)(開発メモのラウンド3、2026-08-10〜2026-08-11)
- 音のリングが足りなくなったときに 0 で埋めていたところを、直前の音から約6ms で 0 へ下げ、戻るときは約3ms で上げる形にしました(`ce_audio.c`)。実機の録音からは、この違いは測れませんでした(開発メモのラウンド34、2026-08-31)
- 音のリングの大きさは、Sound Config で 12 / 24 / 48 / 96 KB から選べます(中はサンプル数で、6144〜49152)。既定は 24576 です(`ce_audio.c`)。前のコアで、フレームスキップ 4 のまま、リングを 6144 から大きくしたら(24576 か 49152。どちらだったかは記録にありません)、録音の途切れは1秒に約4.22回から約0.36回になりました(開発メモのラウンド34b、2026-08-31)
- 体感では、前のコアのフレームスキップ 4 で、重い場面のほかは音が途切れず良好でした(開発メモのラウンド35、2026-08-31)

## 入力

- キーは、`ce_input.c` の `CeInputPoll()` が `GetAsyncKeyState` で毎フレーム読みます
- `ce_input.c` の名前の表(`kVkNames`)では、Brain のボタンは Voice が 0xDC、Function が 0x14、Forward が 0x21、Previous が 0x22 です
- 斜め(右上など)の行は、1つのキーで2方向を押します。`CeInputPoll()` で全部をいったん0にしてから、押されている行の2方向を1にします。斜めの入力が効くことを実機で確かめました(開発メモのラウンド28、2026-08-18)

## ダイアログ

- アプリを起動して最初に、メインメニューを開いたまま ROM 選択のダイアログを開くと、2つのダイアログが混ざって表示されました(実機のスクリーンショット)。2回目からは崩れませんでした(開発メモのラウンド17〜ラウンド19、2026-08-14)
  - 次の3つは効きませんでした: ダイアログが出たあとにフォントを当てる(ラウンド17)、両方のダイアログを `RedrawWindow` で描き直す(ラウンド19)、起動した直後にプロセスを1回起動し直す(ラウンド20)(どれも 2026-08-14)
  - メインメニューを `EndDialog` で閉じてから ROM 選択を開く形にしたら、崩れなくなりました(実機)(開発メモのラウンド22、2026-08-14)
  - メインメニューを開いたまま ROM 選択を開く形に戻したら、同じ崩れがまた出ました。今は、閉じる直前のメインメニューの画面を `BitBlt` でビットマップに写し、ROM 選択の後ろに描いています(`ce_main.c` の `CeMenuSnapTake()`・`CeMenuSnapPaint()`)。同時に開いているダイアログはいつも1枚です。実機で確かめました(開発メモのラウンド65、ラウンド66、どちらも 2026-09-27)
- ステートセーブで、「セーブしますか？」のダイアログを閉じてから「セーブしました。」のダイアログを開いていたときは、そのあいだにメインメニューのボタンが一瞬見えました。1枚のダイアログの中で文とボタンを替える形(`ce_main.c` の `SaveStateDlgProc`)にしたら、出なくなりました(実機)(開発メモのラウンド63、2026-09-07)
- ROM の読み込み中は、`retro_load_game()` を呼ぶ前に、そのとき画面に出ているウィンドウへ `GetDC` で直接「読み込み中...」を描いています(`ce_main.c` の `CeShowLoadingScreen()`)。表示を実機で確かめました(開発メモのラウンド16、ラウンド23、どちらも 2026-08-14)
- ROM 選択では、左右キーでページを送ります。1ページは6行です(`CE_FILELIST_PAGE_SIZE`)。最後のページの端数は空の行で埋めています(`FillFileList()`)。端数のページへも送れることを実機で確かめました(開発メモのラウンド38、2026-09-01)
- ページを `LB_GETCURSEL` から求めていた版では、実機で、端でループしない、送った先が一番上の行に来ない、途中から1行ずつしか動かない、の3つが出ました。ページを `s_fileListPage` で持ち、`LB_SETTOPINDEX` → `LB_SETCURSEL` → もう一度 `LB_SETTOPINDEX` の順にしたら、3つとも直りました(`ce_fileopen.c` の `FileListCtrlProc`)(開発メモのラウンド61、ラウンド61b、2026-09-04)
- ROM 選択で A〜Z のボタンを押すと、選択が動きました。`ce_fileopen.c` の `FileListCtrlProc` で、空白以上の `WM_CHAR` を元のリストボックスに渡さずに捨てています(開発メモの「v1.0.4 の1回目」、2026-10-07、コミット b88b95c、タグ v1.0.4)
- RC の座標はダイアログ単位(DLU)で、画素ではありません。Input Config は高さ 176 DLU では、決定ボタンの下が画面から欠けました。全体を 4 DLU 上げて高さ 172 にしたら直りました(実機)(開発メモのラウンド38、2026-09-01)
- アイコン(.ico)には AND マスクを入れます。Pillow で書いた .ico にはマスクが無かったので足し、実機でアイコンを確かめました(開発メモの「v1.0.1 の1回目」「v1.0.1 の2回目」、どちらも 2026-10-02、コミット 5596b83、タグ v1.0.1)

## ファイルと設定

- 設定は `AppMain.exe` と同じフォルダの `PopGBA.cfg` に書きます。起動したときは読むだけで、書くのは ROM を選んだときと、設定の画面を閉じたときです(`CeConfigSave()` の呼び出し元)(開発メモの「v1.0.1 の2回目」、2026-10-02)
- `AppMain.exe` を日本語のフォルダ(「アプリ」)に置くと、「追加アプリ」から起動したときに BIOS を読めませんでした。ログでは、`GetACP()` は起動の方法によらず 1252 で、`WideCharToMultiByte(CP_ACP, …)` で変換したフォルダ名は「???」になっていました。CeOpener から起動したときは読めることがあり、同じ exe でも起動のたびに成功と失敗が入れ替わりました(開発メモのラウンド3の後半、2026-08-11)
- PopGBA は `GetShortPathNameW` を使っていません。実機の `coredll.dll` から `GetProcAddress` で取ろうとしたら、取れませんでした(実機のログ)(開発メモのラウンド3の後半、2026-08-11)
- 今は、`CE/compat/stdio.h` で `fopen` を `ce_fopen_utf8()`(`ce_fopen_utf8.c`)に置き換え、UTF-8 のパスを `MultiByteToWideChar(CP_UTF8, …)` で戻してから `_wfopen()` で開いています。`-Icompat` はコアのファイルにも効くので、コアが BIOS・ROM を開く `ce_filestream.c` の `fopen()` もここを通ります(開発メモのラウンド62、2026-09-05)。日本語を含むフォルダの ROM を開けることを、実機で確かめました(開発メモの「v1.0.1 の1回目」、2026-10-02)
- カートリッジのセーブ(`.srm`)は、ROM と同じフォルダに書きます。コアの SRAM の大きさは、ゲームによらずいつも 0x20000 バイトです(`libretro.c` の `retro_get_memory_size()`)(開発メモの「v1.0.2 の1回目」、2026-10-03)
- 30秒ごとの自動保存で、SD の `fclose()` が 144〜1,925ms かかり、そのあいだメインのループが止まりました。音のスレッドと waveOut は動き続け(スレッドの間隔は最大36ms)、音のリングが空になって、録音では最大1,845ms の無音になりました(リングは 6144)。このときゲームは SRAM を変えていませんでした(開発メモの「音が途切れる件(mai_nurse)の2回目」、2026-10-07)
- 30秒ごとの自動保存は、中身が読み込んだとき、または前に書いたときと同じなら書きません(`ce_main.c` の `CeSaveSramIfChanged()`)。30秒・60秒の所で音が途切れないことを、実機の録音で確かめました(開発メモの「v1.0.5 の1回目」、2026-10-07、コミット b9d5d74、タグ v1.0.5)
- 終了のときの保存も、同じく中身が変わっていなければ書きません。ゲームの中でセーブしてからメニューの「終了」で終わっても、セーブが残っていることを実機で確かめました(開発メモの「v1.0.6 の1回目」、2026-10-07、コミット 7b0a826、タグ v1.0.6)
- `.srm` がまだ無いゲームでは、メニューを開いたとき・別の ROM を開くときも、SRAM が読み込んだ直後から変わるまで書きません(`ce_main.c` の `CeSaveSramCheckpoint()`)。セーブしないゲームで `.srm` ができないこと、`.srm` が無い状態から始めてセーブしたゲームを続けられることを、実機で確かめました(開発メモの「v1.0.7 の1回目」「v1.0.7 の2回目」、どちらも 2026-10-09、コミット 21fa3e3、タグ v1.0.7)
- 前のコアで JIT を ON にしていると、ステートセーブが失敗のメッセージになりました。ステートの一時バッファを `malloc` から `VirtualAlloc` に変えたら直りました(実機)。今のコードも `VirtualAlloc` を使っています(`ce_main.c` の `CeSaveState()`)(開発メモのラウンド28、ラウンド29、どちらも 2026-08-18)

## BIOS

- 正規の BIOS(`gba_bios.bin`)が無くても、ゲームは動きます。BIOS が見つからないときや中身が正しくないときは、コアに入っているオープンソースの BIOS を使います(`libretro.c` の `retro_load_game()`)。そのため、BIOS が原因で ROM の読み込みが失敗することはありません(開発メモの「v1.0.2 の1回目」、2026-10-03、コミット e829e5e)
- BIOS は、cfg の `BiosDir`(v1.0.0・v1.0.1 の BIOS 選択画面で選んだフォルダ)、`AppMain.exe` と同じフォルダ、開いた ROM と同じフォルダ、の順に探します。前の2つは起動したときに1回だけ調べます(`ce_main.c` の `ResolveBiosSystemDir()`)(開発メモの「v1.0.2 の1回目」、2026-10-03)

## 終わり方

- 終了は `ce_main.c` の `CeShutdown()` から `ExitProcess()` を直接呼びます。順番は、音を止める → `.srm` の保存 → `retro_unload_game()`・`retro_deinit()` → タスクバーを出す → mutex を閉じる →(ROM の切り替えで起動し直すときだけ)新しいプロセスの `ResumeThread()` → `ExitProcess()` です(開発メモの「CeOpener・CERestorer から起動して終了すると固まる件の見直し」、2026-10-07)
- タスクバーは、`ce_main.c` の `CeShowShellChrome()` で、`FindWindowW(L"HHTaskBar", NULL)` で見つけたウィンドウに `ShowWindow` を呼んで出しています
- CeOpener や CERestorer から起動すると、終了したあとに画面が真っ暗になる、または操作を受け付けなくなることがありました。USB ケーブルと電池を抜いてから入れ直すと戻りました。終了のときに `.srm` を書かないテスト用の exe(デバッグログ OFF)では、CeOpener・CERestorer から10回起動して終了し、1回も固まりませんでした。前にどのくらいの割合で起きていたかは分かっていません(開発メモの「2026-10-05」の節、「CeOpener・CERestorer から起動して終了すると固まる件の見直し」、2026-10-07)

## デバッグの進め方

- アプリが例外で落ちたときは、[Brain Exception Reporter(BER)](https://github.com/Sgch/ber) で例外とレジスタを記録しました(開発メモのラウンド6、2026-08-12、ラウンド15、2026-08-14)
- BER の PC の値は、strip する前の .o からリンクし直した exe で `arm-mingw32ce-nm -n` で関数を引き、`objdump -d` で命令を見ました(開発メモのラウンド15、2026-08-14)
- PopGBA には、落ちたときに呼ばれる処理を入れていません。実機の `coredll.dll` からは、`SetUnhandledExceptionFilter` を `GetProcAddress` で取れませんでした(実機のログ)。前のコアでは、翻訳したブロックの番地を、落ちる前にログに書いておく方法で、落ちた所を探しました(開発メモのラウンド10、2026-08-12、ラウンド44、ラウンド48、どちらも 2026-09-02)
- デバッグログ(Video Config の「デバッグログを有効にする」)は既定で OFF です。`CeVideoInit()` で設定を読んでから有効にするので、それより前の行はログに出ません(`ce_log.c`・`ce_video.c`)(開発メモのラウンド31、2026-08-30、ラウンド34b、2026-08-31)
- ログを ON にすると、`perf: retro_run`・`perf: blit`・`perf: audio_push` の行が出ます。各行の頭にはミリ秒の時刻(`GetTickCount()`)が付きます。速さの話は、この行の数字で確かめました(開発メモのラウンド14、2026-08-13〜2026-08-14、ラウンド60、2026-09-02)
- `audio underrun` のログは500回に1回(1回目、501回目…)、`ring overrun` は最初の3回だけ出ます(`ce_audio.c`)。ある区間に行が無くても、その区間で起きていないとは限りません(開発メモの「音が途切れる件(mai_nurse)の1回目」、2026-10-07)
- `CeLog()` は1行ごとにファイルを開いて閉じます。ログを ON にしたとき、2行のあいだが 940ms 空き、録音ではそこに 875ms の無音がありました(開発メモの「音が途切れる件(mai_nurse)の2回目」、2026-10-07)
- 音の途切れは、実機で録った音と、ログの時刻を合わせて調べました(開発メモのラウンド34、2026-08-31、「音が途切れる件(mai_nurse)の2回目」、2026-10-07)
- `CE/Makefile` の `CE_EXTRA_CFLAGS` で、ファイルを変えずにコンパイルの定義を足せます(開発メモのラウンド44、2026-09-02)

## 対応していないもの・動作を確かめていないもの

- 時計(RTC)を使うゲームの、時計の動作は確かめていません。PopGBA はコアの時刻の元の設定に答えないので、コアの既定のまま動きます(開発メモの「v1.0.2 の1回目」、2026-10-03)
- PopGBA は、振動、通信ケーブル、ワイヤレスアダプタ、傾き・光・ジャイロのセンサー、カードeリーダーには対応していません。振動・通信は、コアからの問い合わせに PopGBA が答えていません(開発メモの「v1.0.2 の1回目」、2026-10-03)
- メニューを通らずにアプリが閉じたとき(ウィンドウが外から閉じられたとき)の保存は、試す方法が無く、確かめていません(開発メモの「v1.0.6 の1回目」、2026-10-07)
